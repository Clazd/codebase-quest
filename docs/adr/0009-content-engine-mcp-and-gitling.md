# 0009. Content engine, MCP server, setup and Gitling

- Status: Accepted
- Date: 2026-10-19
- Phase: 06

## Context

Phase 06 makes AI optional, keyless and safe: the user's own agent prepares the
world's text through MCP, `cq setup` registers it, and Gitling answers with
verified citations. Everything any source produces must pass one validation path.

## Decision

- **One engine, many sources.** `packages/content` defines content types, zod
  output schemas, style guides, items built from fact sheets (plus masked code for
  dialogue), and `validateContent`: schema → limits/escaping (no links, markup,
  markdown, control characters, relayed instructions, credential or answer talk)
  → grounding (every code-like identifier must come from the fact sheet, its doc
  or quoted code) → citations (real file, real lines, overlapping an item symbol)
  → answer-leak guard. `produce()` retries once with the reasons, moves to the
  next provider, and finally uses the template, which is itself validated. The
  browser-safe entry exports dialogue, validators, search and guards; Node parts
  (fact sheets, disk cache, settings, Ollama/Anthropic providers) are `./node`.
- **Doc comments are data.** The Phase 05 doc-quote rule no longer quotes a first
  sentence that looks like markup or an injected instruction.
- **Cache.** `.codequest/cache/content/<sha1(repoId, commit, entityId, type,
  promptVersion, source)>.json` plus an alias by code hash, so unchanged entities
  reuse content across commits. Only validated AI output is cached; templates are
  generated on demand. `repoId` is the repository name for now.
- **Search.** BM25 over names (×3), paths (×2), doc comments, signatures and up to
  400 masked code tokens, with a light stemmer. It is generated by `cq play`
  beside `world.json` (`search.json`), not by the pure world generator, because it
  needs file text. The game searches locally, so level 1 works offline.
- **MCP server.** `cq mcp` (stdio, official SDK 1.32.1) exposes the twelve tools
  from the plan. Inputs are zod schemas; results carry provenance and wrap
  repository text in `{ untrusted: true }`; every result passes `AnswerGuard`.
  `cq_create_quest` validates a minimal quest YAML (talk/visit/read steps) and
  writes nothing until Phase 15. Sampling is used only when the client advertises
  it; otherwise questions queue for `cq_wait_for_question` while a bridge loop
  has polled in the last minute.
- **Bridge.** `cq play` hosts `/bridge` on its loopback server. Clients must say
  hello with a 256-bit token within 3 s. Browsers must use the server's own origin
  and may only be the game; non-browser clients may only be agents. Messages are
  zod-validated, ≤ 64 KiB, and limited to `focus`, `playerState` and
  `gitlingQuestion`; anything else closes the socket. The token is written to
  `~/.codequest/sessions/<hash>.json` (0600) for the MCP server and reaches the
  page only in the URL fragment. Agent answers are validated again by `cq play`
  before the game shows them, with their level.
- **Modes.** AI is Off by default (`~/.codequest/config.json`, `cq ai`). Off means
  templates + search and no outbound network; agent questions are forwarded only
  in agent mode. Ollama must be on loopback. API mode uses `@anthropic-ai/sdk`
  0.131.0: `claude-opus-5-5` by default (per-type overrides), explicit
  `output_config.effort` (default `medium`), structured outputs via
  `beta.messages.parse` + `zodOutputFormat`, a cached system prefix, server-side
  refusal fallback (`fallbacks: "default"`, shown in settings), `stop_reason`
  checks with template fallback, streaming for chat, and the Batches API for bulk
  prebuilds (no fallbacks there). A daily budget and cost meter (list prices) stop
  requests before they exceed it. API mode needs per-repository consent that shows
  what is sent; keys come only from the SDK's credential resolution and have no
  field in any file.
- **Setup.** Modeled on REA's reviewed transaction: plan first, `--dry-run`
  writes nothing, explicit approval (`--yes` only with `--client`; non-interactive
  runs report `needs_confirmation`), detection is not permission (without
  `--client` only existing registrations are refreshed). Malformed or symlinked
  configs or a config changed since planning block the whole transaction before
  any write. JSON edits use `jsonc-parser` and TOML edits are textual, so unrelated
  entries and comments stay. The first `.codequest.backup` is kept; a differing
  original gets a `.recovery` copy. Writes are atomic and read back. A manifest
  in `~/.codequest/setup-state.json` lets uninstall restore the original bytes
  exactly when nothing changed since setup, or else remove only our entry; the
  skill is removed only if unchanged. Claude Desktop on Windows uses the MSIX
  package-private config when it exists. No REA code is reused.
- **Answer-leak guard.** Answer keys are never part of any request or tool
  output by construction (no AI path reads puzzle data). The guard additionally
  blocks text containing distinctive keys (≥ 8 characters, whitespace-normalized)
  of an active fight; shorter keys such as `7` or `"open"` occur in ordinary code
  and cannot be matched without blocking everything. Phase 07 registers fights.
- **Tests and CI.** Vitest sets `CQ_HOME` to a temporary folder so tests never
  touch the user's settings, sessions or setup state.

## Consequences

The game is fully playable with AI Off; agent mode needs no key. Every later
content type (combat explanations, quest narration, issue mapping) only needs a
schema, a style guide, items and a template. Phase 07 receives the hint ladder
and guard; Phase 13 the cache format; Phase 15 the quest validator. A real
agent's end-to-end prebuild (Claude Code) is a manual step; automated tests use a
scripted MCP client.
